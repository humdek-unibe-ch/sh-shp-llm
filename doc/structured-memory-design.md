# Structured Memory — Design

**Status:** implemented in plugin v1.10.0 (design agreed 2026-11-26, sections moved to the key registry and made optional 2026-11-27). Where the code adds to or differs from this text, see "Implementation notes" at the end.
**Scope:** `sh-shp-llm` global memory (`LlmMemory*Service`, memory worker, new `llmMemoryEditor` style)

## Problem

Today every memory update lets the LLM rewrite the whole memory. It returns a free-text
`memory_text` plus an unstructured `memory_object`. Researchers asked for memory shown as a
list of facts where each row can be edited or deleted. With free text there are no rows, and
asking the LLM to "delete X" is not reliable: it rewrites everything, can reword unrelated
facts, and tends to keep history inside the text ("the user's name was changed from …").

## Goals

1. Memory is a list of short facts (items), optionally grouped into sections.
2. Sections are optional and configured per memory key (no hard-coded default).
3. Users can edit, delete and add single items directly, **without an LLM call**.
4. Free-text change requests through a rule + LLM keep working, but the LLM can only touch
   items it is asked about.
5. Nothing that works today breaks (see "What stays the same").

## Non-goals

- Typed / field-based memory shapes (e.g. `name`, `birthdate` columns). The `format` tag
  leaves room for this later; not built now.
- Purging facts from history. Delete removes an item from the **current** memory only;
  history rows keep their snapshots.
- Admins editing other users' memory in `moduleLlmMemory` (possible later reuse of the
  same row view).

## What stays the same

Storage is **not** changed:

- Current table (`llm_memory`): still **one record per user + memory key**, upserted by
  `LlmMemoryStorageService::upsertCurrentMemory()`. Same columns: `memory_text`,
  `memory_json`, `memory_version`, `rule_id`, `source_type`, …
- History table: still one appended row per change, with `prev_memory_json`.
- `memory_text` is still filled on every save. It is now **rendered by code** from the
  items (markdown, grouped by section label) instead of written by the LLM.

So all existing consumers keep working unchanged:

- `data_config` retrieval of `memory_text` (e.g. the Forest `/test-interview` card,
  `retrieve: last`, `current_user: true`, `memory_key = 'global'`).
- Showing `{{memory_text}}` in a markdown section.
- Loading `memory_text` dynamically into LLM context (prompts / chat config via
  `data_config` interpolation).
- Admin memory browser and history views.

Only the **content** of `memory_json` changes shape, and `memory_text` becomes
deterministic.

## 1. Stored shape (`memory_json`)

```json
{
  "format": "items/v1",
  "items": [
    {
      "id": "m_8f3a2c",
      "section": "person",
      "text": "Name: Stefan Kodzhabashev, prefers to be addressed as Baseff",
      "source": "llm",
      "updated_at": "2026-11-26 10:12:04"
    },
    {
      "id": "m_19c2d0",
      "section": "goals",
      "text": "Wants to run 5 km",
      "source": "user",
      "updated_at": "2026-11-26 10:15:40"
    }
  ]
}
```

- `id` — generated by code (never by the LLM), unique within the memory. Short random hex
  with `m_` prefix.
- `section` — must be a section code defined for the key; unknown codes are rejected
  (LLM ops) or not offered (UI).
- `text` — plain text, one fact, trimmed, max length (proposal: 500 chars).
- `source` — `llm` | `user` (who last wrote the item).
- `updated_at` — last change of this item.
- `format` — version tag. A future shape (`fields/v1`) gets its own renderer; readers
  must check `format` before assuming items.

### Rendered `memory_text`

Built by code after every change, in section order from the key config, empty sections
skipped:

```markdown
### Person
- Name: Stefan Kodzhabashev, prefers to be addressed as Baseff

### Goals
- Wants to run 5 km
```

## 2. Per-key section config

Memory keys have a registry since v1.2.0: table `llm_memory_keys` (code, label,
description), managed in the **Keys** tab of the LLM Memory page. The sections are a new
column of that table, `sections_json`, edited per key in the Keys tab (Edit):

```json
[
  {"code": "person",  "label": "Person",  "hint": "Current personal facts only, no history of changes"},
  {"code": "context", "label": "Context", "hint": "Situations, observations, working hypotheses"},
  {"code": "goals",   "label": "Goals",   "hint": "Things the user wants to achieve"}
]
```

- Sections are optional. A key without sections (NULL / empty) is one flat list: items have
  `section` `""`, the prompt says there are no sections and the output schema has no
  `section` field (a section the model sends anyway is dropped, so the fact is kept).
- `label` is the default heading in the UI and the heading in rendered `memory_text`.
  Participants see it translated through the editor's translatable field `memory_labels`
  (`"<key>"`, `"<key>.<code>"`, `"<code>"` → label); `memory_text` is not per language and
  keeps the registry label.
- `hint` is injected into the LLM prompt so it knows what belongs in which section.
- Lives on the key (not on a style) because the memory worker needs it too.
- Read through `LlmMemoryConfigService::getKeySections($memory_key)`; written through
  `LlmMemoryRuleService::updateMemoryKey()` (validated by
  `LlmSettingsValidator::parseKeySections()`).

## 3. LLM updates return operations

The memory worker (`LlmMemoryUpdateService`) sends the LLM:

- the section definitions (code, label, hint) for the key,
- the current items **with ids**,
- the submitted event data / change request (as today),
- the rule prompt and user language (as today).

New output schema (replaces `memory_text` / `memory_object` / `flat_fields` for
`items/v1` keys):

```json
{
  "ops": [
    {"op": "update", "id": "m_8f3a2c", "text": "Name: Stefan Kodzhabashev"},
    {"op": "delete", "id": "m_77aa01"},
    {"op": "add", "section": "goals", "text": "Wants to become a football player"}
  ],
  "change_summary": "Updated name, removed old workplace, added football goal"
}
```

Code applies the ops:

- `add` → new id, `source = llm`; rejected if section unknown or text empty.
- `update` → only `text` (and optionally `section`) of that id; unknown id is skipped.
- `delete` → remove that id; unknown id is skipped.
- Empty `ops` is a valid "nothing to change" answer.
- Then render `memory_text` and save via `saveMemoryUpdate()` as today.

Why ops: items the LLM was not asked about cannot drift, and a user edit made while the
worker was running survives (an op on a since-deleted id is just skipped).

Prompt guidance (built-in system prompt): one fact per item, current state only (no
"was changed from…" history), no invented facts, respect section hints, reuse/update an
existing item instead of adding a duplicate.

## 4. Lazy migration of existing memories

No up-front migration. When the worker loads a memory whose `memory_json` has no
`format: items/v1`:

1. Treat it as zero items.
2. Add the old `memory_text` to the prompt as "legacy memory to convert".
3. Instruct the LLM to return `add` ops that split it into items (plus whatever the
   current event changes).

The editor style shows a legacy memory read-only (rendered `memory_text`) with a note,
until its first update converts it. (Alternative if needed: a "convert now" button that
triggers the same conversion.)

## 5. New style: `llmMemoryEditor`

Component style (`LlmMemoryEditorComponent` / Model / View / Controller) in
`server/component/style/llmMemoryEditor/`. Always works on the **current user's** memory.

### Fields

| Field | Type | Purpose |
|---|---|---|
| `memory_keys` | multi select | Which keys to show/edit (options: the key registry; default: module default key). Several keys are shown one below the other, each with its heading, saved independently |
| `memory_labels` | json, translatable | Headings per language: `"<key>"`, `"<key>.<code>"`, `"<code>"` |
| `display_mode` | select | Layout of the sections: `sections` (default), `accordion`, `tabs`, `cards`, `flat` |
| `allow_add` | checkbox | Show "+ add" per section |
| `allow_edit` | checkbox | Show edit per item |
| `allow_delete` | checkbox | Show delete per item |
| `confirm_delete_text` | text | Confirmation dialog text |
| `read_only_text` | text | Note under a free-text memory that is not converted yet |
| `empty_text` | markdown | Shown when no memory / section empty |
| `label_*` | text | Button labels (add / edit / save / cancel / delete) |

Free-text change requests stay a separate `formUserInput` + memory rule (as on
`/test-interview`). The rule sets `refresh_sections` to the editor section so it reloads
when the worker finishes. Built-in textarea in the style is a possible later addition.

### UI

- One block per section (label from key config), one row per item.
- Row: text; edit (inline input + save/cancel); delete (jquery-confirm).
- "+ add" under each section opens an inline input.
- Edits are AJAX posts to the controller; only the section re-renders.
- Layout (`display_mode`): the item rows and buttons are one shared partial; the layouts
  (`sections`, `accordion`, `tabs`, `cards`, `flat`) only wrap the blocks. `flat` has no section
  to add to, so its "+ add" is shown only when the key has exactly one section. An accordion
  panel / tab is Bootstrap 4 markup; since the body is replaced after each action, the script
  notes the open panel / tab by section code and sets it again on the new body.
- Look: CSS custom properties (`--lme-*`) on `.llm-memory-editor`, plain Bootstrap 4 by
  default; theme classes (`lme-theme-forest`) in the section's `css` field. No DB field.

### Controller actions

`add_item`, `edit_item`, `delete_item`. Each:

1. Loads the current user's row for the `memory_key` of the request, which must be one of the
   section's `memory_keys` (never a user id from the request).
2. Checks `memory_version` sent by the client equals the stored one; on mismatch returns
   "memory changed, reloaded" and re-renders (no silent overwrite).
3. Validates: item id exists, section exists, text non-empty and within max length.
4. Applies the change, renders `memory_text`, saves via `saveMemoryUpdate()` with
   `source_type = user_edit`, `rule_id = 0`. A history row is appended as usual.
5. Output is escaped with `htmlspecialchars` (item text is user/LLM text, not trusted HTML).

Note: `memory_version` is `date('YmdHis')` today (1-second resolution). Good enough for
user edits; if needed, switch to a counter later.

## 6. Delete semantics

- Delete removes the item from the current row (`llm_memory`).
- History keeps the old snapshot in `memory_json` / `prev_memory_json` — **by decision**.
- The form log of the change request (if the deletion came from free text) also stays.
- If a real purge is ever required (privacy request), it is a separate admin feature.

## 7. Migration (SQL, plugin `server/db/vX.Y.Z.sql`)

- New column `llm_memory_keys.sections_json` (the sections of a key).
- New style `llmMemoryEditor` + its fields + `styles_fields`.
- Plugin version bump.
- CMS cache clear required after install.

## Verification criteria

- Existing `data_config` card showing `{{memory_text}}` keeps rendering after an update
  (now in rendered markdown form).
- A legacy free-text memory is converted to items on its first update.
- Free-text request "remove X" deletes only that item; other items are byte-identical.
- Editor: add / edit / delete persist, history row written with `source_type = user_edit`,
  no LLM call made.
- Stale `memory_version` → edit rejected and view reloaded.
- A user cannot edit another user's memory or another key by tampering with the request.

## Implementation notes (plugin v1.10.0)

All decisions above are implemented as written. These are the points the design left open, or
where the code differs in detail.

**Code.** `LlmMemoryItems` (pure functions: read a row, apply ops, render `memory_text`),
`LlmMemoryConfigService::getKeySections()`, `LlmMemoryUpdateService` (worker, ops based), style
`llmMemoryEditor` (`js/ext/llm-memory-editor.js`, `css/ext/llm-memory-editor.css`), the **Memory
Sections** card of the LLM settings, and the migration in `server/db/v1.10.0.sql`.

**Fields of the style.**
- `empty_text` and the `label_*` fields are the core's shared fields of type `text` (the table
  in section 5 says markdown for `empty_text`). The editor shows them as plain, escaped text.
- `confirm_delete_text`, `read_only_text` and `label_save` are new `text` fields; `memory_keys` is a
  multi select of its own field type (`select-llm-memory-keys`, options = the key registry, rendered by
  the same `LlmHooks` method as `memory_rule_ids`); `memory_labels` is translatable `json`.
- `display_mode` is a select of its own field type (`select-llm-memory-display-mode`): its options
  are the lookups `llmMemoryDisplayMode`, rendered by `LlmHooks` like the `llm_interview_*` selects.
  The view accepts the codes in `LlmMemoryEditorView::DISPLAY_MODES` and falls back to `sections`.
- `allow_add` / `allow_edit` / `allow_delete` are checkboxes that count as **on** when the field
  has no value, so an action is only taken away by unticking it.
- Messages that are not CMS fields (conflict, validation, errors) are fixed English, like the
  other messages of the plugin.

**Sections and keys.**
- Memory keys are case-insensitive ("Global" = "global"). A key without sections, one the
  registry does not know, or one whose stored sections cannot be read is one flat list.
- The editor request names its memory key; it must be one of the section's `memory_keys`
  (else 403). Each key has its own body, version check and answer.
- An item whose section the key no longer defines stays in the memory. `memory_text` lists it
  after the configured sections (the section code as heading). The editor shows it after the
  configured sections too, lets the participant edit and delete it, but offers no "+ add" there.
  An LLM `add` into a section the key does not define is skipped; an `update` that leaves the
  item in its current section is accepted.
- `memory_text` writes `<` and `>` of an item as `&lt;` and `&gt;`, because the markdown sections
  that show it let raw HTML through. The editor itself escapes with `htmlspecialchars`.

**`memory_version`.**
- The editor sends the `memory_version` of the row it shows. When only the history is stored
  (storage mode `log`) there is no current row: the id of the latest history row is the version.
- The version has a one-second resolution and the check and the write are not one atomic step, so
  two requests of one participant in the same second can both pass. Accepted: it only concerns
  one person editing in two tabs at once (see "Note" in section 5).
- On a conflict only the editor block reloads. Other sections that show the memory (a markdown
  section with `{{memory_text}}`) change on their next reload or refresh event.

**Worker and editor at the same time.**
- The worker reads the memory again when it applies the ops (after the model answered), so an
  edit the participant made meanwhile survives; an op that names an item deleted meanwhile is
  skipped.
- The stale check (`isNewerEvent`) runs once, when the worker starts. A participant edit keeps the
  `event_at` of the memory it changed (the time of the edit only when there was no memory yet), so
  it never makes a queued rule update stale: an update that was **still queued** when the
  participant edited runs and is applied to the edited memory, like one that already runs.

**Legacy memories.**
- A memory without `items/v1` is read as zero items plus the old text; the prompt then asks for
  `add` ops. If the model's answer cannot be used (after the existing retry) the memory stays as it
  was and the failure is written to the transaction log. The editor shows the old text read-only
  until a conversion succeeded.
- An admin edit in the Users tab of the LLM Memory page is unchanged: it writes `memory_text` and
  `memory_json` as typed. A `memory_json` that is not `items/v1` makes the memory a legacy memory
  again, which the next update converts.
- Dataset cases imported from memory worker calls made before v1.10.0 carry the system prompt and
  schema that were logged then (free text). The Prompt Lab replays them verbatim, so they answer in
  the old shape.

**Not part of this version.** Mobile output of the editor is read-only (sections and items, no
editing). The editor needs the page to accept `POST` and the participant to be allowed to open it;
a guest is stopped by the core access check and never reaches the editor.
